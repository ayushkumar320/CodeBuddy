# Proposal 00 — Storage Model

Status: Draft
Owner: @ayushkumar320
Target: v0.2.0
Supersedes: the implicit storage model in v0.1 where every user-authored
            artifact lives in Postgres
Affects: Proposals 01, 02, 03 (each is annotated below)

## Why this exists

v0.1 stores everything in Postgres: interactions, facts, summaries,
shares, plans (planned), audit log, model calls. Wipe the database and
every fact a developer ever asked the agent to remember is gone. The
file tree carries no evidence that CodeBuddy was ever installed.

That model has three problems:

1. **Portability.** Users cannot commit their context to git. The
   "remember this" the developer asked Claude to do yesterday is
   invisible to a teammate reviewing today's PR.
2. **Coexistence with the markdown ecosystem.** `CLAUDE.md`,
   `.cursor/rules`, `AGENTS.md`, and similar files are how every other
   AI tool reads project context. A database-only product is illegible
   to that ecosystem.
3. **Strategic fragility.** "Store memory in Postgres" is not a
   defensible position against Mem0, Letta, Zep. The Postgres
   dependency is friction that the markdown competitors don't carry.

This proposal flips the model. **Markdown is the source of truth.
Postgres is a derived index that the user can wipe at any time.**

## The decision

| Category | Lives in | Survives DB wipe? |
|---|---|---|
| Memory facts | `.codebuddy/memory/**/*.md` | Yes |
| Plans | `.codebuddy/plans/pln_<id>.md` | Yes |
| Policies | `.codebuddy/policies.yaml` | Yes |
| Project config | `.codebuddy/config.json` | Yes |
| Aggregated agent rules | `.codebuddy/CLAUDE.md`, `.codebuddy/AGENTS.md` (auto-built) | Yes |
| Embeddings | `embeddings` table in Postgres | No — regenerated on reindex |
| Architecture graph | `map_*` tables in Postgres | No — regenerated by parser |
| Plan index | `plan_index` table in Postgres | No — regenerated by reader |
| Risk score cache | `risk_*` tables in Postgres | No — regenerated by assessor |
| Audit log | `audit_log` table | No — telemetry, acceptable to lose |
| Model call diagnostics | `model_calls` table | No — telemetry, acceptable to lose |
| Raw conversation interactions | `interactions` table | No — high-volume, ephemeral |

The invariant: **nothing a user authored requires the database to
survive.** Running `docker compose down -v && docker compose up -d &&
codebuddy reindex` returns the system to a fully-functional state.
The DB is a build artifact, like `dist/`.

Interactions are the one user-adjacent category that stays DB-only.
They are conversation logs, not curated knowledge. The high write
volume makes file-per-interaction wasteful, and they are rarely read
after the session ends. The Memory panel surfaces *facts* and
*summaries* — both markdown — not raw interactions.

## File layout

```
<repo>/
└── .codebuddy/
    ├── config.json               project-scoped config (already exists)
    ├── policies.yaml             risk policy rules (Proposal 03)
    ├── memory/
    │   ├── facts/
    │   │   ├── fact_01jc4xy.md
    │   │   └── fact_01jc4xz.md
    │   ├── summaries/
    │   │   └── sum_01jc500.md
    │   └── decisions/            optional, user-curated
    │       └── 2026-06-21-oauth.md
    ├── plans/
    │   ├── pln_01jc4ww.md
    │   └── pln_01jc4xa.md
    ├── CLAUDE.md                 auto-generated; read-only
    └── AGENTS.md                 auto-generated; read-only
```

All files in `.codebuddy/` are committed to git by default. Users who
want private project memory add `.codebuddy/memory/private/` to their
`.gitignore`. The CLI documents this idiom; it does not enforce it.

`CLAUDE.md` and `AGENTS.md` are flat aggregations regenerated on every
write — they exist so existing AI tools that look for those filenames
find a single, current document instead of having to walk
`.codebuddy/memory/`.

## Database schema role

Three classes of table:

### Index tables — derived from files

```sql
-- Embeddings now key by file path + content hash. Rebuilt on reindex.
create table embeddings (
  id              text primary key,
  namespace_id    text not null references namespaces(id),
  source_path     text not null,                 -- repo-relative .md path
  source_hash     text not null,                 -- sha256 of file content
  source_kind     text not null,                 -- 'fact' | 'summary' | 'plan'
  source_id       text not null,                 -- the id: from front-matter
  vector          vector(384) not null,
  embedding_model text not null,
  created_at      timestamptz default now(),
  unique (namespace_id, source_path),
  index (namespace_id, source_kind)
);
```

`source_id` and `source_kind` are denormalised from the file content
so vector queries do not have to read the file to discover what kind
of artifact they hit. `source_hash` makes incremental reindex cheap:
unchanged file ⇒ skip embed.

### Pure derived tables — regeneratable

- `map_modules`, `map_symbols`, `map_edges` (Proposal 01) — from source code.
- `plan_index` (Proposal 02) — from `.codebuddy/plans/*.md`.
- `risk_cache` (Proposal 03) — from the join of the above.

### Telemetry tables — append-only, ephemeral

- `audit_log` — operations performed; useful for debugging, acceptable
  to lose.
- `model_calls` — provider call diagnostics; useful for tuning,
  acceptable to lose.

### Tables removed in v0.2

The following v0.1 tables are deprecated. Their contents are migrated
to files by `codebuddy migrate to-files` (see below).

- `facts` → `.codebuddy/memory/facts/fact_<id>.md`
- `session_summaries` → `.codebuddy/memory/summaries/sum_<id>.md`
- `shares` → embedded inside the target fact's front-matter as a
  `sharedFrom:` field; the relationship is no longer a separate row.
- `interactions` *stays* in the DB — see rationale above.

## The reindex contract

`codebuddy reindex` is the single command that brings the database
back into agreement with the filesystem. It must be:

- **Idempotent.** Running twice produces the same DB state.
- **Incremental by default.** Reads the file hash from `embeddings`;
  skips files whose hash hasn't changed.
- **Full-rebuild on demand.** `codebuddy reindex --full` truncates the
  index tables before scanning.
- **Concurrent-safe.** Holds a single Postgres advisory lock keyed by
  namespace_id; a second `reindex` waits for the first.

Triggered automatically:

- On `codebuddy serve` startup, after migrations.
- On every `codebuddy remember` / `codebuddy forget` (single-file
  reindex of the affected path).
- On every plan write via the Plan Panel CLI.
- Optionally on file save via `codebuddy memory watch` (analogous to
  the map watcher).

## Reads — how recall works after the pivot

Recall behaviour is unchanged from v0.1's user-visible contract:
`recall({ sessionId, query, budget?, callerModel?, conflictMode? })`
still returns `{ system, messages, stats }`.

Internally, the planner queries `embeddings` for vector similarity,
joins to `embeddings.source_path`, and **reads the file at query time**
to get the body. This costs one filesystem `read` per included
candidate (cheap; files are small) but means we never store content
duplicated in the DB.

The body is cached in process memory for the lifetime of the recall
call — repeated reads of the same path inside one recall do not hit
disk twice.

## Migration path from v0.1

`codebuddy migrate to-files` is a one-shot command shipped in v0.2.0
that:

1. Reads every row from `facts` and `session_summaries`.
2. Writes one markdown file per row under `.codebuddy/memory/`.
3. Truncates the old tables.
4. Runs `codebuddy reindex` to populate `embeddings` against the new
   files.
5. Writes a `MIGRATION.md` summary at the repo root that the user can
   review and commit.

The command is interactive on first run and shows a dry-run of file
counts and the directory tree before writing. `--non-interactive`
skips the confirmation for CI use.

v0.1 users who do not migrate keep working — the v0.2 code path
detects the old schema and falls back to the v0.1 read path with a
deprecation warning on every recall. The warning includes the
`codebuddy migrate to-files` command. v0.3 removes the fallback.

## What this means for each downstream proposal

| Proposal | What changes |
|---|---|
| **01 Architecture Map** | Unchanged. Source is the code, not user content. |
| **02 Plan Panel** | Rewrites tables out of the schema; plans live as files. See revised 02 for details. |

## Open questions

1. **Markdown vs MDX vs YAML for facts.** Markdown with YAML
   front-matter is the de facto standard. Considered: pure JSON
   (machine-friendly but hostile to humans), TOML (less common). Stick
   with YAML front-matter.
2. **Per-fact size limit.** Facts can grow large enough to be
   wasteful. Soft warning at 4 KB, hard limit at 64 KB (configurable).
   Users who want longer documents put them under
   `.codebuddy/memory/decisions/` and link them from a shorter fact.
3. **Conflict in `subject` across files.** Two files claiming
   `subject: deployment.region` with different objects are exactly the
   conflict that the existing `conflictMode` planner option handles.
   No new behaviour needed.
4. **What if the user edits a memory file by hand?** Encouraged. The
   next reindex picks up the new hash and re-embeds. Audit log records
   "manual edit detected" with the path; the agent can recall it as a
   signal that something changed outside its own writes.
5. **What about binary attachments (screenshots, diagrams)?** Out of
   scope for v0.2. The schema accommodates a `attachments:` array in
   the front-matter for v0.3.

## Rejected alternatives

- **Pure markdown, no database.** Loses semantic vector search, the
  Architecture Map's joinable queries, and the Risk Panel's
  cross-signal aggregation. All three are SQL-shaped problems; trying
  to do them on files would mean reinventing a query engine.
- **Pure database, no files.** The status quo. Loses portability,
  coexistence with the CLAUDE.md ecosystem, and PR-reviewability.
- **Hybrid where users choose per-fact.** Adds a configuration knob
  for no real gain. Either commit to the model or don't.
- **SQLite as the index.** Considered. Loses pgvector. Requires a
  pure-JS HNSW implementation. Rejected because Postgres is already
  required for the Architecture Map's joinable queries; adding SQLite
  is one more dependency for no win.
- **Storing the markdown body in the embeddings row alongside the
  vector.** Cheaper recall (no file read) but means a stale DB serves
  outdated content after the file is edited. Better to read the file
  every recall.

## Definition of done for v0.2

- `.codebuddy/memory/` and `.codebuddy/plans/` exist on a fresh
  `codebuddy use`.
- Every `codebuddy remember` writes a markdown file in addition to
  inserting into Postgres.
- `codebuddy reindex` rebuilds embeddings from files alone, without
  reading the old DB tables.
- `docker compose down -v && docker compose up -d && codebuddy
  reindex` returns recall results identical to pre-wipe (verified by
  an integration test that wipes the DB mid-test).
- `codebuddy migrate to-files` migrates a v0.1 install without data
  loss; a checksum comparison test confirms parity.
- README leads with "your context is markdown" and points at the
  `.codebuddy/` folder as the artifact users own.
